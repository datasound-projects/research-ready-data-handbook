Foundations · Read first

Raw data is not research data

The philosophy that governs every step in this handbook.
00

Every dataset that arrives from an exchange, a broker, a vendor or an internal capture system is raw. Raw means: unverified timestamps, unverified units, unknown gaps, unknown bad ticks, unadjusted corporate actions, unexamined boundaries, and a distribution nobody has looked at. Feeding raw data into a model does not produce research — it produces confident numbers about a dataset that does not describe the market.

Professional desks therefore run every dataset through a Financial Data Validation & Conditioning Pipeline before research begins. The purpose of that pipeline is frequently misunderstood, so state it precisely:

Principle
The goal is not to make the data look clean. The goal is to make the data economically meaningful and statistically usable. A dataset scrubbed of every unusual value is a dataset scrubbed of every crash, squeeze, liquidation cascade and regime break — which is exactly where risk lives and where alpha is paid. You are conditioning data, not beautifying it.

Three consequences of that principle run through the whole handbook:

  • Diagnose before you touch. Detection, classification and repair are separate steps with separate outputs. Nothing is deleted or filled until it has been classified.
  • Extreme is not the same as wrong. A +20% move can be a liquidation cascade (keep it, model it) or a decimal error (repair it). The value alone cannot tell you which. Context can.
  • Every repair is logged. Raw data is kept immutable. Repairs, imputations and masks live in a separate layer with method, timestamp and uncertainty attached, so any result can be traced back and any repair can be reversed.

How to use this handbook

The thirteen chapters are in chronological pipeline order. Follow them top to bottom for every new dataset and you will not skip a failure mode. Each chapter ends with a “things that actually go wrong” list and a stage checklist — the checklists concatenated are the dataset approval form in Chapter 13. Every step ships with a Python snippet; the companion package ResearchReadyPy implements the entire pipeline 1:1 and produces the visual conditioning report.

Validate · Chapter 01

Data ingestion & raw data validation

Interrogate the file before you interrogate the market. Nothing is trusted, everything is checked, nothing is deleted.
01

Before you compute a single return, interrogate the file itself. Ingestion validation is boring, mechanical, and catches more real-world research failures than any statistical technique in this book. Desks automate all of it and refuse the file if it fails.

1.1Source & vendor validation

Know exactly where each field comes from and how it was produced. The questions to answer, once per source, in writing:

  • Origin: exchange direct feed, consolidated tape, vendor aggregation, or someone’s scrape? Aggregated crypto prices (an “index” across venues) behave differently from single-venue prices — they are smoother and can hide venue-specific dislocations.
  • Point-in-time or backfilled? Many vendors silently restate history (fix bad ticks, restate fundamentals, add delisted names). If the file you download today differs from what you would have seen live, your backtest sees a cleaner world than the strategy ever will. Prefer point-in-time snapshots; if unavailable, record the download date and treat history as potentially revised.
  • Survivorship: does the universe include delisted, bankrupt, merged and renamed instruments? A universe of today’s survivors overstates historical returns and understates risk. This is one of the largest silent biases in equity research.
  • Reliability record: keep a per-source incident log (outages, bad prints, revisions). Cross-check a sample of rows against a second independent source before trusting a new vendor.

1.2Schema and data-type validation

Lock the expected schema in code and validate every delivery against it. Silent dtype changes (prices arriving as strings, volume as int32 that overflows, timestamps as epoch-milliseconds one day and epoch-seconds the next) are classic vendor incidents.

1.3Timestamp validation and timezone normalization

Timestamps are the spine of a time series; every later step assumes they are right. The standing rule on every desk: store everything in UTC, tz-aware, at ingestion. Convert to exchange-local time only when you need session logic (opens, closes, auctions), and do the conversion with a proper timezone database, never a fixed offset — daylight-saving transitions are where fixed offsets die. Also pin down the bar-timestamp convention: does 09:30 label the bar’s open or its close? Mixing conventions across sources shifts every feature by one bar.

Watch out
Epoch-unit confusion is a real incident class. 1_700_000_000 is November 2023 in seconds and January 1970 in milliseconds. If dates cluster in 1970 or in the year 55978, the vendor changed epoch units mid-file. Detect by checking the magnitude of raw integer timestamps before parsing.

1.4Duplicate detection

Two different problems hide under “duplicates”: exact duplicated rows (harmless to drop, but log how many), and conflicting duplicates — the same timestamp with different prices. The second kind means two feeds were merged or a correction was appended; it needs a resolution rule (keep last correction, keep primary source), not a blind drop_duplicates().

1.5Missing records vs. missing values (calendar-aware)

A missing value is a NaN in a row you have. A missing record is a row that should exist and does not — and you can only see it against the correct trading calendar. Crypto trades on a true 24/7 grid; equities trade in exchange sessions with holidays and half-days. Checking an equity series against a naive daily grid “finds” thousands of fake gaps (weekends); checking crypto against a business-day calendar hides real ones.

1.6Unit, scale and currency consistency

Cents vs. dollars, pence vs. pounds (LSE data is famous for GBX), per-share vs. total, basis points vs. percent, contract price vs. notional, and redenominations. A unit break looks exactly like a 100× price jump. Scan for order-of-magnitude discontinuities and reconcile every one against a known cause (split, redenomination, unit change) before believing it.

1.7Symbol and ticker validation

Tickers are not stable identifiers. They get reused (a delisted ticker reassigned to a new company), changed (FB→META), and they differ across venues (BRK.B vs BRK-B vs BRKB). Crypto pairs add their own traps: BTCUSD vs BTCUSDT vs BTCUSDC are different instruments with different prices. Map everything to a stable internal ID (FIGI/ISIN/permno-style, or your own) at ingestion, and keep a ticker-history table. Sanity-check that each symbol’s price level is in its plausible range — a “BTC” series at 1.07 is an FX pair wearing the wrong label.

1.8Internal OHLCV consistency

Add a stale-bar check: long runs where open = high = low = close with zero volume usually mean the feed froze and forward-filled itself — disguised missing data (Chapter 3), not real trading.

1.9Corporate action adjustments — only where they apply

Corporate actions are mainly a concern for equities, ETFs and indices: stock splits, dividends, mergers, spin-offs, ticker changes. A 2-for-1 split halves the price overnight without anyone losing money; unadjusted, it looks like a −50% crash and destroys every return-based computation.

Professional practice keeps two series, permanently:

SeriesWhat it isWhat it's for
Raw (unadjusted)The prices that actually printed on the tapeExecution analysis, tick validation, reconciling against the venue, microstructure work
AdjustedHistorical prices scaled by cumulative split/dividend factors so the series is economically comparable through timeReturns, features, labels, backtests — all research
Hard rule
Do not blindly adjust every asset class. Crypto and spot FX have no splits or dividends — running an equity adjustment routine on them corrupts the data. Futures need roll stitching (building a continuous contract across expiries, usually back-adjusted), which is a different operation with its own artifacts: back-adjusted continuous futures can go negative and their levels are not tradeable prices. Adjust each asset class with the logic that belongs to it.

But the lesson generalizes both ways — do not treat every extreme value as an error, and do not treat every extreme value as a market event. Things that actually go wrong
  • Vendor silently restates history — yesterday’s download and today’s disagree. Hash and version every delivery.
  • Timestamps in exchange-local time joined against UTC data: every feature is off by hours, twice a year it's off by a different amount (DST).
  • Bar-label convention mismatch (bar stamped at open vs. at close) silently shifts all features by one bar.
  • Volume column switches between base-currency and quote-currency units mid-history (common in crypto vendor exports).
  • Equity history without delisted names: survivorship bias inflates every backtest built on it.
  • int32 volume overflow on high-activity days turns big volume into negative volume.
Stage checklist
  • Source documented: origin, point-in-time status, survivorship coverage, incident log started.
  • Schema & dtypes validated against the locked spec; delivery rejected on mismatch.
  • All timestamps parsed, tz-aware UTC, strictly increasing, no duplicates, none in the future; bar-label convention recorded.
  • Exact and conflicting duplicates counted and resolved by rule.
  • Missing records enumerated against the correct trading calendar.
  • Unit/scale discontinuities reconciled against documented events.
  • Symbols mapped to stable IDs; ticker-history table updated.
  • OHLCV internal consistency violations extracted; stale frozen bars flagged.
  • Raw and adjusted series both stored (where adjustment applies); raw kept immutable.
  • Extreme values flagged for Chapter 7 triage — nothing deleted yet.
Validate · Chapter 02

Know what financial time series are

Fat tails, clustering, regimes and one-way time: the structural facts that make naive cleaning destructive.
02

Financial time series are a hostile environment for standard data-science habits. Before diagnosing or repairing anything, internalize what this data is — because every cleaning decision in later chapters depends on it.

2.1The seven properties that change everything

PropertyWhat it means in practiceWhat it forbids
Non-stationarityPrice levels drift and trend; the distribution moves. Returns are closer to stationary, but their variance still shifts.Fitting anything on price levels; computing one mean/std for the whole history and using it everywhere.
Fat tailsExtreme returns occur orders of magnitude more often than a Gaussian predicts. Daily equity/crypto returns show excess kurtosis of 5–50+.3-sigma outlier rules; Gaussian likelihoods; assuming a 10-sigma print “can't be real”.
Volatility clusteringBig moves follow big moves. |returns| are strongly autocorrelated even when returns are not.Treating observations as i.i.d.; imputing quiet values into a stressed period.
Regime changesThe data-generating process itself switches: 2017 crypto, March 2020, a rate-hike cycle. Parameters fitted across regimes describe none of them.Cleaning or normalizing with statistics pooled across regimes.
Noise dominanceSignal-to-noise is brutally low; real predictive effects are small and fragile.Aggressive smoothing/denoising that plausibly deletes the entire signal along with the noise.
Microstructure effectsBid–ask bounce, discrete tick sizes, irregular trade arrival, venue quirks. At high frequency these dominate the series.Treating tick data like a smooth curve; interpolating through the bounce; ignoring the price grid.
Temporal dependencyOrder is information. Today depends on yesterday; information flows one way.Row shuffling, random train/test splits, any operation that lets the future touch the past.

2.2Why financial data cannot be cleaned like a tabular dataset

Standard tabular hygiene — drop outliers beyond 3 standard deviations, mean-impute the gaps, standardize with full-sample statistics — is actively destructive here:

  • Dropping >3σ points on a fat-tailed series deletes precisely the crash and squeeze days — the observations that determine real risk and that many strategies live on.
  • Mean/median imputation injects values from the wrong regime and creates fake stability inside stressed periods.
  • Full-sample statistics leak the future into the past (Chapter 10).

The canonical example, which recurs through this handbook: a rare +15% BTC daily move could be contamination (bad tick, venue error) or a genuine market event (liquidation cascade, ETF headline). The number alone is identical in both cases. Only context — surrounding ticks, volume, other venues, the news tape — separates them. That is why classification (Chapter 7) is a step of its own, and why “remove outliers” is never an instruction on a professional desk.

2.3Measure the structure before touching the data

Run a structure report on every new series and keep it with the dataset. It calibrates every later decision: how heavy the tails are (imputation model choice), how strong the clustering is (whether gaps can be filled independently), whether levels or returns should be modelled.

Field note
What the numbers typically say. Daily BTC: excess kurtosis often 8–20, |r| lag-1 autocorrelation 0.15–0.35, return lag-1 autocorrelation within noise of zero. If your series reports excess kurtosis near 0, either the asset is unusual or someone already “cleaned” it — investigate before trusting it.
Things that actually go wrong
  • A suspiciously Gaussian financial series usually means upstream filtering already destroyed the tails.
  • Structure measured across an obvious regime break (e.g. pre/post a crash) is an average of two different markets — segment first, then measure.
  • Applying daily-data intuition to tick data: at high frequency, microstructure noise, not price dynamics, dominates every statistic.
Stage checklist
  • Structure report computed and stored with the dataset (tails, clustering, stationarity, autocorrelation).
  • Levels vs. returns decision made explicit for all later modelling.
  • Known regime breaks in the sample period listed before any pooled statistic is computed.
  • Team agreement recorded: extreme values are classified, never auto-removed.
Diagnose · Chapter 03

Missing data: the full taxonomy

Where the holes are, what shape they have, and why they exist. Nothing gets filled in this chapter.
03

Missing data in finance is not one problem — it is a family of problems with different causes, different risks and different correct treatments. The first job is a complete inventory: where are the holes, what shape are they, and why are they there. Repair comes later (Chapters 4–6).

3.1The taxonomy of gap shapes

The two boundary rows deserve emphasis because they are routinely mishandled: they are not imputation problems at all. The start boundary is missing history — there is nothing before the series began, so a 200-day indicator simply cannot exist for the first 199 rows. The end boundary is missing future — a 20-day forward label cannot exist for the last 20 rows. Chapter 8 turns this into an exact valid-sample calculation.

3.2Profile every gap

3.3Missingness mechanisms: MCAR, MAR, MNAR

Shape says how to reconstruct; mechanism says how dangerous the hole is. The standard statistical taxonomy, translated into market reality:

MechanismDefinitionFinancial exampleRisk level
MCAR — missing completely at randomMissingness unrelated to anythingRandom API failure, dropped packetsLow: any sensible method works; mostly a variance cost
MAR — missing at randomMissingness depends on observed variablesLow-volume assets drop out more often; gaps cluster in overnight sessionsMedium: condition the reconstruction on those observed variables
MNAR — missing not at randomMissingness depends on the hidden values themselvesExchange goes down because of the extreme move; venue halts during the crash; stale marks in stressed illiquid marketsHigh: the gap is informative. Naive filling systematically hides exactly the extreme states you care about
Hard rule
MNAR gaps around market stress are the most dangerous holes in finance. If data disappears during extreme events and you fill the gap with anything smooth, you have manufactured a calmer history than the market ever offered. Every risk number and every backtest downstream inherits that lie. MNAR-suspect gaps get conservative treatment: reconstruct with wide uncertainty, flag heavily, and consider excluding the window from training rather than repairing it.
Things that actually go wrong
  • Forward-filled vendor data hides gaps as frozen prices — run the stale-bar check from Chapter 1 before profiling, or your gap table will be empty and wrong.
  • Gaps counted against the wrong calendar (weekends “missing” in equities, real 3 a.m. outages invisible in crypto).
  • Cross-sectional holes treated column by column when the assets are cointegrated — you throw away the best reconstruction information there is.
  • Zero volume recorded as zero price by some feeds: a zero is not a NaN, and it is much more destructive.
Stage checklist
  • Stale/frozen segments reclassified as missing before profiling.
  • Gap table produced: every run's position, length, boundary status.
  • Sampling regularity measured; series formally declared regular or irregular.
  • Mechanism evidence computed (missingness vs. volume, vs. volatility) and operational causes recorded.
  • MNAR-suspect windows explicitly listed for conservative handling.
Diagnose · Chapter 04

Classify before you impute

A formal diagnosis step between finding holes and filling them — with a reviewable decision table as its output.
04

The single most common amateur mistake with financial gaps is reaching for fillna() in the same line that discovered them. Professional pipelines insert a formal step between detection and repair: classification. Its output is a decision table — a reviewable artifact — not a filled series.

Principle
Never blindly fill missing values. First determine: what type of gap is it? Why is it missing? How long is it? How high is the uncertainty? Only then does the method choose itself. Diagnosis and treatment are different steps performed by different code.

4.1The five questions, in order

  1. What shape? Single point, short block, long block, boundary, irregular, cross-sectional (Chapter 3 taxonomy).
  2. Why is it missing? MCAR / MAR / MNAR evidence plus operational cause (outage log, halt calendar, vendor incident).
  3. How long, relative to the data’s memory? A 3-bar gap in daily data is small; a 3-hour gap in tick data spans thousands of events. Judge length in units of the series’ autocorrelation, not wall-clock.
  4. How high is the uncertainty? Gaps in calm regimes are cheap to reconstruct; gaps during stress (check realized vol around the hole) carry wide error bars whatever the method.
  5. What is the downstream use? Data feeding a volatility model must not have its variance smoothed away; data feeding a long-horizon trend feature tolerates smoother fills. The consumer constrains the method.

4.2A working classifier

4.3The decision table is the deliverable

The output of this stage is the gap table from Chapter 3 with three columns appended: class, mechanism_evidence, recommended_method. On a desk this table is what gets reviewed — a human (or a strict rule set) signs off on it before any value is written. It also becomes part of the dataset’s permanent audit trail: six months later you can answer “why is 2024-03-12 imputed, with what, and how sure were we?” in one lookup.

Do
Emit a classification artifact

Gap table → classes → chosen methods → sign-off → only then repair. Every fill is traceable to a reviewed decision.

Don’t
Repair inside the detection loop

df[col] = df[col].interpolate() as a “preprocessing line” makes every later statistic a mixture of market and invention, with no record of which is which.

Things that actually go wrong
  • One global fill method applied to all gaps “for consistency” — consistency across different problems is a bug, not a feature.
  • Gap length judged in wall-clock time instead of in bars/events — a weekend is not a gap in equities and three hours is an eternity in ticks.
  • Classification skipped for “just a few NaNs”: the few NaNs are usually the halt during the crash.
Stage checklist
  • Every gap answered on all five questions.
  • Decision table produced: gap → class → mechanism → method → expected uncertainty.
  • MNAR-suspect and regime-length gaps escalated for explicit sign-off.
  • Nothing has been filled yet.
Repair · Chapter 05

Imputation methods and when to use them

From the dangerous defaults to Kalman smoothing to Palomar's heavy-tailed stochastic EM — matched to the gap classes of Chapter 4.
05

With gaps classified, choose the reconstruction. This chapter goes from the methods you should rarely use, through the workhorse state-space tools, to the heavy-tailed EM approach designed specifically for financial series, and ends with a selection cheat sheet.

5.1Why the “easy” methods are dangerous

  • Forward fill: acceptable only as an explicit “last known value” state variable (with an age counter), never as a price.
  • Linear interpolation: uses the point after the gap, i.e. the future. Tolerable for offline historical reconstruction if flagged; forbidden anywhere near live features (Chapter 10). It also draws a straight line through what was really a volatile path — variance inside the gap collapses to zero.
  • Mean/median imputation: injects a whole-sample level into a local context; in a trending series the filled value can be years away from its neighbours. Never appropriate for prices.

5.2Kalman filtering and smoothing (the workhorse)

Model the series as a latent state observed with noise; where observations are missing the filter simply propagates its prediction, and the backward (RTS) smoother then blends information from both sides. You get a fill and an uncertainty for every point — which is the minimum standard for research-grade imputation. A compact local-level implementation:

5.3Autoregressive (AR) conditional imputation

Fit an AR model on the observed data and fill each hole with its conditional expectation given the neighbours. For a single interior point under AR(1) this is a precision-weighted blend of the forward prediction from y[t-1] and the backward implication of y[t+1]. Simple, fast, respects the series’ own dynamics — and it is the skeleton the next method builds on.

5.4The Palomar approach: heavy-tailed AR with stochastic EM

Prof. Daniel P. Palomar’s group (HKUST) developed the imputation approach that practitioners treat as the reference for financial series, implemented in the R package imputeFin (Liu & Palomar). Three ingredients define it:

  • Autoregressive modelling — the series (typically log-prices or returns) follows an AR process, so temporal dependency is respected rather than ignored.
  • Heavy-tailed (Student-t) innovations — the shocks are t-distributed, not Gaussian.
  • Stochastic Expectation–Maximization — missing values and model parameters are estimated jointly, iterating draws of the missing data with parameter updates.

Why the heavy tails matter: financial returns are not normally distributed — they contain fat tails and extreme-but-valid market events (Chapter 2). A Gaussian imputation model treats a crash next to a gap as near-impossible, so it drags the fill toward calm values and understates uncertainty. A Student-t model expects occasional violence: it down-weights extreme neighbours when estimating the parameters (so one crash doesn’t corrupt the fit) while still allowing the filled values to live in a fat-tailed world.

AdvantagesLimitations
Designed for financial time series; respects temporal dependency instead of filling points independentlyDepends on the AR + t model being roughly right; misspecification biases the fills
Handles non-Gaussian behaviour far better than Gaussian/simple methods — robust parameter estimates, realistic uncertaintyLess flexible for highly nonlinear dynamics (structural breaks inside the gap, complex regime behaviour)
Statistically consistent joint estimation of parameters and missing values, with uncertainty for freeIterative: heavier than interpolation; needs convergence monitoring on short series

ResearchReadyPy implements this as impute_student_t_em() — a stochastic-EM AR(1)-Student-t imputer via the Gaussian scale-mixture (IRLS) representation with a state-space smoother, returning fills, per-point uncertainty and the fitted (phi, sigma, nu). For maximum-fidelity production use, Palomar’s original imputeFin in R remains the reference implementation.

5.7Golden rules for every imputation, whatever the method

Golden rules
  • Never impute the target/labels — a manufactured label is a manufactured result.
  • Every filled point carries a flag column (*_was_missing) and an uncertainty (*_imputed_std).
  • Imputation runs per instrument and never blindly across a documented regime break.
  • Downstream models can (and should) receive the flags as features or sample weights.
  • The repair log records: gap id, method, parameters, uncertainty, who/what approved it.
  • Re-run the Chapter 2 structure report after imputation: volatility and tail statistics must not have visibly collapsed.
Repair · Chapter 06

Diffusion-style generative reconstruction

Many plausible paths instead of one confident lie: ensembles, uncertainty, and the hard limits of generation.
06

For long gaps and for uncertainty estimation, a single “best” fill is the wrong shape of answer. Generative, diffusion-style reconstruction produces many plausible paths and lets you keep the whole distribution.

6.1What diffusion models are, in one paragraph

Diffusion models are generative probabilistic models. Trained on data, they learn to reverse a gradual noising process, which gives them a way to sample from p(clean data | observed data) — the distribution of complete series consistent with what you actually saw. In financial data work they are used for denoising, missing-data reconstruction (conditional generation given the observed points), scenario generation, and uncertainty estimation (the spread of the samples is the error bar). Time-series imputers in this family (CSDI-style conditional score-based models) are active research and increasingly practical; the honest desk view is that they are powerful for representation and uncertainty, and dangerous if mistaken for truth.

6.2The ensemble workflow

The simplest member of the family needs no neural network at all: a constrained stochastic bridge that walks from the left anchor with locally-fitted drift and fat-tailed shocks and is pinned to the right anchor. It is a legitimate baseline, it demonstrates the whole workflow, and it is what you should implement before reaching for a learned model:

6.3What the reconstruction is — and is not

Hard rule
A generated path is not a trading signal. Diffusion-style reconstruction is a data representation layer, an uncertainty estimation layer, and a latent market-state extraction tool. It must not directly become a signal: the generator will happily manufacture structure, and a strategy can end up trading the model's imagination. Downstream models may consume the mean path together with its uncertainty; they may never treat sampled paths as history that happened.
Watch out
Realistic is not the same as correct. A generated path can look perfectly plausible — right volatility, right clustering — and still be historically wrong about what occurred inside the gap. Always validate reconstructions economically and statistically: do ensemble moments match the surrounding market? do cross-asset relationships hold through the filled window? does an independent venue's data (if any survives) fall inside the interval? If the true path matters (e.g. a halt during a crash), no generator can conjure it — widen the uncertainty or exclude the window.
Things that actually go wrong
  • Averaging many paths and then treating the smooth mean as if it had normal volatility — the mean of paths is smoother than any path; keep the spread.
  • Training a learned generator on the same history you later “reconstruct” for backtesting — a quiet form of leakage.
  • Ensembles anchored on a contaminated endpoint (Chapter 7 not yet run): every path inherits the bad tick.
Stage checklist
  • Long gaps reconstructed as ensembles, not single paths.
  • Mean, interval and full path set stored; uncertainty travels with the data.
  • Reconstructions validated against surrounding moments and any independent source.
  • Documented rule in place: generated data never feeds signals directly.
Repair · Chapter 07

Outliers vs. contaminants

Rare-but-real versus invalid-by-construction: opposite objects, opposite treatments, and the evidence that separates them.
07

This is the distinction that separates professional financial data work from generic data cleaning, so it gets stated in full: an outlier and a contaminant are different objects with opposite treatments. “Remove outliers” is never the instruction. “Classify extremes, keep the real ones, repair the fake ones, log everything” is.

OutlierContaminant
DefinitionA rare but real observation — the market actually did thatAn invalid observation — the market never did that
ExampleBTC +20% on a liquidation cascade, a macro shock, a major headline999 999 999 printed between ticks at ~100 300: bad tick, API error, wrong decimal, wrong symbol
Information contentHigh — tail risk and (often) alpha live hereZero — pure measurement error

7.1Evidence, not thresholds

No single statistic separates the two — both are extreme by construction. Desks use a consensus of independent evidence:

  • Robust statistics (MAD z-score): flags candidates. Median/MAD are used instead of mean/std precisely because fat tails corrupt the classical estimates.
  • Reversion behaviour: the classic bad-tick signature is a one-bar spike that fully reverses next bar. Real shocks usually persist or continue.
  • Volume confirmation: real violent moves happen on violent volume. A 20% move on dead volume is suspicious.
  • Cross-venue comparison: did Coinbase, Kraken and OKX print it too? A move that exists on one venue only is a venue artifact (or a thin-book event — still not the market).
  • Market context: halt calendars, news timestamps, macro releases, funding events. A spike at a CPI release is context-confirmed.
  • Model residuals: Kalman innovations or diffusion-reconstruction error — how surprising is the point to a model of the local dynamics?
  • Tick plausibility: does the price sit on the instrument’s tick grid? Off-grid prices in tick data are mechanically impossible.

7.2A triage implementation

7.3Treatment

Do
Winsorize features with past-only rolling stats, if you must

Clipping engineered features at rolling past-only quantiles is a defensible robustness choice — documented, reversible, leak-free.

Don’t
Winsorize or delete raw prices by a global threshold

A full-sample 3σ clip deletes every crisis (destroying risk information) and uses the future to define “normal” (leakage, Chapter 10).

Things that actually go wrong
  • Flash crashes are the hard case: real trades, mostly reverted, economically meaningful. They are outliers with reversion — volume and multi-venue prints separate them from bad ticks. When in doubt: keep, flag, document.
  • Repairing a contaminant but leaving its ghost in derived columns (returns, vol) computed earlier — always recompute downstream columns after repair.
  • Cross-venue checks against a venue that shares the same upstream aggregator: false confirmation.
  • Thresholds tuned until the data “looks nice” — that is curve-fitting your own cleaning.
Stage checklist
  • Every extreme point labelled valid / outlier / contaminant / uncertain with recorded evidence.
  • Outliers kept; modelling plan for tails documented (t-likelihoods, EVT, vol models).
  • Contaminants repaired via local model; raw preserved; audit entries written.
  • Uncertain points escalated — not silently guessed.
  • Derived columns recomputed after repair.
Assemble · Chapter 08

Temporal boundary problems

Giller's principle: the beginning is missing history, the end is missing future, and only the middle is research.
08

Graham Giller’s boundary principle, which every research dataset must obey: a raw dataset is not automatically usable from its first row to its last. Both ends are silently invalid, for different reasons, and the invalid zones must be computed — not eyeballed.

8.1The start boundary: missing history

Every lookback in the feature set claims rows at the start: rolling windows, EWMA burn-in (an EWMA needs several multiples of its span before initialization effects wash out), volatility estimators, normalization windows. The start boundary of the dataset is set by the largest of them.

8.2The end boundary: missing future

8.3The valid-sample formula

Watch out
Boundaries multiply in nested computations. A z-scored SMA(200) with a 252-day normalization window needs 200 + 252 rows of warm-up, not max(200, 252) — the z-score's window consumes rows of an input that is itself only valid after row 200. Compute boundary cost through the whole feature graph, or measure it empirically: the first row where every feature column is non-NaN when built with strict min_periods.
Things that actually go wrong
  • Libraries that emit values before the window is full (default min_periods=1): the early “SMA(200)” is really an SMA(7) and behaves completely differently. Always set min_periods=window.
  • Interior long gaps re-create start boundaries after them: a 200-day feature is invalid again for 200 rows after a multi-month hole.
  • Backtests whose stellar early years sit entirely inside the warm-up zone.
  • Padding the start with synthetic history to “rescue” the boundary — the indicator then measures your padding.
Stage checklist
  • Max feature lookback computed across the full feature graph (nesting included).
  • Max label horizon computed across all labels.
  • Valid window derived by formula; in_valid_window mask attached to the dataset.
  • Interior regime gaps re-checked for reborn start boundaries.
  • Training, validation and evaluation code all consume the mask.

Feature engineering validity checks

Windows, lags, normalization and joins: the mechanical checks that keep conditioned data conditioned.
09

Features are where a conditioned dataset most often gets silently re-corrupted. Before any feature enters the research set, it passes these validity checks — all of them mechanical, all of them automatable.

9.2Reference implementations

Principle

Things that actually go wrong
  • Report dates vs. availability dates: Q4 fundamentals “dated” Dec 31 were published in February. Join on availability.
  • Features built on the adjusted price series where the adjustment factor was computed with knowledge of future splits/dividends — use point-in-time adjustment (adjust as of t) for anything feeding a backtest.
  • Resampling with labels at the interval start while data accrues through the interval (the 09:00 bar containing 09:00–10:00 trades, used “at 09:00”).
  • Cross-sectional ranks/z-scores computed over the full panel including assets not yet listed at t.
Stage checklist
  • Every feature's window, lag and data dependencies declared in a spec table.
  • All rolling ops trailing with strict min_periods; no centered windows anywhere.
  • All normalizations rolling/expanding, past-only.
  • All joins as-of on availability timestamps.
  • Feature stationarity eyeballed/tested; level-drifting features transformed.
Assemble · Chapter 10

Look-ahead bias prevention

One rule, ruthlessly enforced: nothing at time t may depend on anything after t. With the tests that prove it.
10

Look-ahead bias is the most expensive bug in quantitative finance: it produces beautiful backtests and dead strategies, and it is invisible until real money finds it. The rule is one line; this chapter is the enforcement machinery.

Hard rule
The model may only know what was knowable at prediction time. Wrong: the feature at day 10 uses data from days 11–20. Right: the feature at day 10 uses days 1–10. Everything else in this chapter is this rule applied to the sneaky cases.

10.3The point-in-time recomputation test (run this on everything)

The one automated test that catches whole classes of leaks at once: recompute each feature using only data up to t, and compare with the stored value at t. If truncating the future changes the past, the feature is leaking.

10.4Purged splits with embargo (leak-free evaluation)

Things that actually go wrong
  • “It's only the scaler” / “it's only interpolation” — the most successful leaks are the ones that feel too small to matter.
  • A pipeline that passes the PIT test on prices but joins one auxiliary table (news counts, on-chain data) without as-of semantics.
  • Leakage through the target: any feature computed from a window that overlaps the label window is partially the label.
  • Backtest results that improve when you re-download the data: the vendor backfilled; your history got smarter than you were.
Stage checklist
  • Every transform fitted past-only (scalers, PCA, encoders, vol estimates).
  • Point-in-time recomputation test wired into CI for every feature.
  • Evaluation uses purged + embargoed splits sized to the label horizon.
  • Adjustment factors and vendor snapshots handled point-in-time.
  • A final untouched holdout period exists and has been used exactly once.
Assemble · Chapter 11

Label generation & validation

The one column allowed to contain the future — built so the future cannot leak anywhere else.
11

Labels are the most dangerous column in the dataset, because they are the only column that is allowed to contain the future — and therefore the easiest place to smuggle the future into the features. Label generation happens after conditioning and boundary computation, and it gets its own validation pass.

11.1Forward returns done correctly

The forward h-bar return at time t uses prices at t and t+h, both of which must come from the conditioned price series. The last h rows cannot have a label. They stay NaN and are excluded from training — they are the end-boundary from Chapter 8, now made concrete.

Hard rule
Never impute a label. A label is the ground truth you are trying to predict. Filling a missing label with interpolation or a model manufactures the target — the model then learns your imputer, not the market. Rows with missing or boundary labels are dropped from training, never filled.

11.2Triple-barrier labels

Fixed-horizon returns treat a +5% spike that mean-reverts and a slow +5% grind identically, and they ignore path risk entirely. The triple-barrier method (López de Prado) labels each event by which barrier the path touches first: an upper profit-taking barrier, a lower stop-loss barrier, or a timeout at the vertical barrier. Barriers scale with local volatility so the label means the same thing in quiet and violent regimes.

Watch out
Timeout is only legal inside the sample. A label of 0 means “neither barrier was touched within the horizon”. Near the end of the data you cannot know that — the path is simply cut off. That is why the loop stops at n − horizon and the tail stays NaN instead of being labeled a fake timeout.

11.3Overlap, weights and label audits

With a 20-bar horizon computed every bar, consecutive labels share up to 19 bars of the same path. They are not independent observations; naive IID training and naive t-statistics will both overstate your confidence. The standard treatments: sample every k bars, or keep all rows but weight each by its average uniqueness (inverse of how many other labels overlap it), and always evaluate with the purged, embargoed splits from Chapter 10.

Do
Recompute labels from the conditioned series

Labels inherit every repair decision. If you re-impute or re-adjust prices, every label downstream is stale and must be regenerated.

Don’t
Reuse labels computed on raw prices

A label built on an unrepaired bad tick is a label for an event that never happened. The model will hunt for a pattern that predicts a typo.

Things that actually go wrong
  • Vertical-barrier timeouts near the dataset edge silently labeled 0 instead of NaN — the classic way the end boundary leaks back in.
  • Volatility for barrier widths computed with centered or full-sample estimators — the label width itself becomes a look-ahead channel.
  • Class balance that changes drastically across regimes: a barrier multiple tuned in a quiet year produces almost all timeouts in a violent one.
  • Labels regenerated after a data re-download without regenerating features, or vice versa — version both together.
  • Meta-information leakage: dropping rows where the label is missing before a train/test split shifts the split point itself.
Stage checklist
  • Labels computed on the conditioned, point-in-time-correct price series.
  • End boundary rows are NaN; assertion wired into the pipeline.
  • Barrier widths / horizons use past-only volatility.
  • Overlap handled: sampling, uniqueness weights, or both; splits purged + embargoed.
  • Label audit (counts, balance, tail check) stored with the dataset version.
Approve · Chapter 12

Regime & distribution checks

Is it one market or several? Answer before the model answers it for you.
12

The dataset is now clean, bounded and labeled. The last analytical question before approval: is it one market or several? Financial series switch regimes — calm to crisis, trending to mean-reverting, one liquidity structure to another. A model trained blindly across regimes learns a blend that describes none of them, and a validation split that straddles a regime break measures the break, not the model.

12.1Volatility regimes: the 80% solution

Most regime structure in most assets is volatility structure. A past-only EWMA volatility estimate cut into quantile buckets gives you an honest, leakage-free regime tag in ten lines — and it is the tag that most changes model behavior in practice.

Watch out
Full-sample quantiles are look-ahead. Cutting volatility into terciles using quantiles of the whole history tags 2020 using knowledge of 2024. Use expanding (or rolling) quantiles as above, and accept that early rows carry no regime tag — that is just another start boundary.

12.2Change-points: where did the series break?

Regime tags answer “what state is bar t in?”. Change-point detection answers “where does the data-generating process shift?” — exchange migrations, tick-size changes, contract redesigns, the day a stablecoin depegged. A simple binary segmentation on the mean of log(r²) (a variance proxy) finds the big structural breaks without any heavy dependency.

12.3Distribution drift between train and test

Before approving any split, compare the distributions the model will see. A two-sample Kolmogorov–Smirnov test on returns (and on each feature) between the training window and the test window tells you whether “out-of-sample” secretly means “out-of-distribution”. Drift is not a reason to abort — it is a reason to know, to report, and possibly to train regime-aware.

Field note
HMMs and clustering: optional, powerful, easy to abuse. Gaussian-mixture or hidden-Markov regime models (e.g. hmmlearn) recover richer states — trending vs choppy, calm vs stressed — but they are fitted on the full sample by default, which makes their state path look-ahead. If you use them for features, fit them expanding/rolling. Fitting once on all data is acceptable only for reporting and split design, never as a model input.
Do
Design splits around the regime map

Report per-regime sample counts; make sure the test period is not a single regime the training set has never seen — or if it is, say so on the approval form.

Don’t
Train one model across an obvious structural break

If the contract, tick size, venue or monetary policy changed the process, everything before the break may be a different asset wearing the same ticker.

Things that actually go wrong
  • Regime tags produced by a full-sample HMM quietly used as a model feature — a look-ahead channel with a scientific costume.
  • A test set that is 100% one regime (e.g. only the 2021 bull run) reported as “out-of-sample performance”.
  • Change-points caused by the data plumbing (vendor switch, session change) misread as market regime shifts — check the audit log first.
  • Stationarity checked once on the full series, never per segment: a series can pass ADF globally and still be three different processes glued together.
  • Drift dismissed because “returns are always fat-tailed” — the KS test is comparing shapes, not tails only.
Stage checklist
  • Past-only volatility regime tag attached to every bar (NaN in warm-up).
  • Structural change-points detected, cross-checked against the audit log and vendor history.
  • Train/test drift report generated for returns and all features.
  • Splits reviewed against the regime map; single-regime tests flagged on the approval form.
  • Any regime model used as a feature is fitted strictly past-only.

13.2Reproducibility: the part everyone regrets skipping

Three habits make the whole pipeline auditable. Immutable raw: the vendor file is written once, checksummed, and never edited; all conditioning produces new versioned artifacts. Deterministic runs: the pipeline is a script with pinned dependencies and a seed, not a notebook of manual edits; re-running it on the same raw file yields byte-identical output. An audit log that answers “why is this value here?” for every repaired cell: timestamp, rule, method, parameters, before/after. When a backtest looks too good eighteen months from now, this log is how you find out what happened in ninety seconds instead of ninety hours.
